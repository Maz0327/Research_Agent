# docs/authoritative/spec/Retention_and_Deletion.md

**Purpose:** Make 30‑day retention + hard delete enforceable across DB and storage.

---

## 1) Retention rule (authoritative)

### 1.1 Retention window
- Jobs are retained for **30 days** after completion.

### 1.2 When to set expires_at
When a job transitions into a completed terminal state:
- `completed`
- `completed_with_warnings`

The system MUST set:
- `expires_at = completed_at + 30 days`

### 1.3 Time semantics
- `expires_at` must be stored as `timestamptz`.
- Store in UTC.
- UI shows **days remaining** computed from `expires_at`.

---

## 2) Required DB fields

The `jobs` table MUST contain:
- `expires_at` timestamptz (nullable until completion)
- `deleted_at` timestamptz (nullable)
- `retention_warned_at` timestamptz (nullable)

Index requirement:
- index on `expires_at` where `deleted_at is null`

---

## 3) UI countdown + warning policy

### 3.1 Countdown
UI MUST show a daily countdown (days remaining) for any job with `expires_at`.

### 3.2 Warnings
Warnings MUST be displayed at **{7, 3, 1}** days remaining.

### 3.3 Anti-spam rule
The backend and/or frontend must not spam repeated warnings.

Canonical rule:
- If a warning is shown today, set `retention_warned_at = now()`.
- Do not show another warning on the same day.

---

## 4) Hard delete scope (authoritative)

A hard delete MUST remove:

### 4.1 Database
- Delete the job row after storage cleanup succeeds.

### 4.2 Supabase Storage
Only delete objects referenced by the job.

#### Documents bucket
Delete (if present):
- any doc JSON objects referenced by job manifest/doc paths
- `research/{job_id}/attachments/*` (PDFs/zips generated by user request)

#### Screenshots bucket
Delete:
- screenshot objects referenced in the job config and/or manifest

**Important:** Screenshots are always job-scoped in this system.
There is no global screenshot pool.

---

## 5) Cleanup scheduling and endpoint

### 5.1 Cron schedule
- Daily at **3:00am America/New_York** (cron provider may be UTC-based)

### 5.2 Maintenance endpoint
- **POST** `/maintenance/retention/cleanup`
- Requires header: `X-Maintenance-Token`
- Token must match env var `MAINTENANCE_TOKEN`

Server behavior:
- Invalid token → 401
- Valid token → enqueue cleanup task and return quickly

### 5.3 Cleanup task behavior (authoritative)
Cleanup task must:
1) query expired jobs (e.g., `expires_at < now()` and not deleted)
2) for each job:
   - delete storage objects (documents + attachments + referenced screenshots)
   - then delete job row
3) record logs/warnings for failures

Failure semantics:
- If storage deletion for a job fails, do NOT delete the DB row (prevents orphaned blobs going “untracked”).
- Continue processing other expired jobs.

---

## 6) Storage MIME allowlist requirement

Because PDFs and zips are generated, documents bucket MUST allow:
- `application/json`
- `application/pdf`
- `application/zip`

If you cannot expand the allowlist, create a second private bucket for exports.
